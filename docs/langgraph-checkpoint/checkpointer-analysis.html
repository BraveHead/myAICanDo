LangGraph Checkpointer 数据结构与关联关系分析

以本项目 literary agent 一次真实盖茨比问答会话为样本，拆解 PostgresSaver 的持久化机制
项目：myAICanDo 样本 thread：literary:9ec4f893-…7635e622f624 驱动：@langchain/langgraph-checkpoint-postgres 日期：2026-07-04

一句话总览：项目里存在两套彼此独立的存储——业务侧 assistant_threads（给 UI 展示的会话消息，key 是原始 threadId），和 LangGraph 侧由 PostgresSaver.setup() 自动建的 4 张 checkpoint 表（存 agent 运行的完整状态机轨迹，key 是 agentId:threadId）。两者通过 createAgentThreadId() 拼接的 thread_id 关联。本文聚焦后者。

§0代码入口

在 src/lib/agent/core/agent-runner.ts：

// createAgentCheckpointer()  —— 有 DATABASE_URL 就用 Postgres，否则内存
const postgresSaver = new PostgresSaver(getPostgresPool());
await postgresSaver.setup();   // ← 自动建 4 张表

// createAgentThreadId()  —— 用 agentId 前缀隔离同一前端会话的不同 agent
function createAgentThreadId(agentId, threadId) {
  return `${agentId}:${threadId}`;
}

setup() 执行的建表 DDL 位于 node_modules/@langchain/langgraph-checkpoint-postgres/dist/migrations.js，共建 4 张表：checkpoint_migrations、checkpoints、checkpoint_blobs、checkpoint_writes。

§1三张表各是什么角色

表一句话定位主键
checkpoints每一步的"快照索引"——记录这一步引用了哪些 channel 的哪个版本(thread_id, checkpoint_ns, checkpoint_id)
checkpoint_blobs真正的"状态数据仓库"——按 channel+version 存实际内容 (BYTEA)(thread_id, checkpoint_ns, channel, version)
checkpoint_writes"待落盘的中间写"——某步任务产出、尚未合进下一快照的增量(thread_id, checkpoint_ns, checkpoint_id, task_id, idx)
checkpoint_migrations只记 schema 版本号，无业务数据(v)

三张数据表的第一列全是 thread_id——它是把它们绑在一起的总外键。checkpoint_ns（本项目均为空串 ''）是子图命名空间，此处未用。

§2thread_id 命名：agentId 前缀隔离

前端一个会话 UUID 73ae2ead-…，经不同 agent 前缀拼成互不相干的 thread_id：

weather:73ae2ead-...
demo:73ae2ead-...
literary:73ae2ead-...

于是 checkpoints 表里，同一前端会话下的 weather / demo / literary 各占独立的行，LangGraph 状态互不串。实测库中出现过 demo:e0ac2f30-… 与 weather:e0ac2f30-… 共享同一 UUID 的情况，正是此机制。

为什么需要用 agentId 隔离？

核心原因：一个前端 threadId 对应的"一次会话"，底层可能被多个不同的 agent 处理，而每个 agent 的 LangGraph 状态必须互相隔离。 threadId 和 agent 是两个维度：

维度取值由谁决定含义
threadId73ae2ead-…前端 UI 生成一个对话窗口 / 会话
agentIdweather / literary …后端按请求路由具体哪个 agent 在处理

关键在于：同一个 threadId 下，不同轮次可能命中不同 agent。比如在同一对话框里先问天气（→ weather agent），又贴一段小说让它分析（→ literary agent）——前端 threadId 没变，但底层换了 agent。

如果直接用裸 73ae2ead-… 当 thread_id，weather 和 literary 会写进同一条时间线，后果：

问题后果
历史串味literary 续跑时读到 weather 留下的 tool_call、系统提示残留，上下文被污染
checkpoint 链断裂两个 agent 交替写，parent_checkpoint_id 会指向"另一个 agent 的快照"，状态机错乱
工具 / systemPrompt 不匹配weather 历史里有 get_weather 的 tool_call，literary 并无此工具，恢复状态时可能报错

加前缀后，同一 UUID 下每个 agent 各留各的记忆链（weather:73ae2ead-… / literary:73ae2ead-…），互不干扰。

这也解释了为什么要分两套存储

给 UI 展示消息的业务表 assistant_threads 用的是裸 threadId——UI 视角就是"一个连续对话"，不关心底层换没换 agent；而 LangGraph 引擎需要 agentId:threadId，因为每个 agent 是独立的状态机，绝不能串。

视角key关注点
UI / 业务threadId一个连续对话，展示所有消息
LangGraph 引擎agentId:threadId每个 agent 的独立状态机，不能串

§3checkpoints：一条单向链表

样本 thread 的 5 个 checkpoint，靠 parent_checkpoint_id 指回上一行，构成可回溯的时间线：

step -1  59d005e3b23a   parent=null      ← 用户输入进入
step  0  fdbfff889324   parent=59d0...   ← agent 首次推理
step  1  96d611d4a949   parent=fdbf...   ← 发起工具调用
step  2  44a94fee8182   parent=96d6...   ← 工具结果回填
step  3  503b5efc4ea5   parent=44a9...   ← 生成最终答案

每走一步 graph 就落一个快照 → 一轮 tool-calling 对话产生 5 行。metadata->>'step' 是步号，source 为 input/loop。

§4checkpoints → checkpoint_blobs：靠 version 号引用（核心机制）

checkpoints 不直接存状态内容，而是存一张"版本清单" channel_versions（在 checkpoint JSONB 字段里）：

step 0:  {messages:2, __start__:2, branch:to:model_request:2}
step 1:  {messages:3, __start__:2, __pregel_tasks:3, branch:to:model_request:3}
step 2:  {messages:4, __start__:2, __pregel_tasks:4, branch:to:model_request:4}
step 3:  {messages:5, __start__:2, __pregel_tasks:4, structuredResponse:5, branch:to:model_request:5}

而 blobs 表存的正是这些 (channel, version) 的实际数据。关联方式：checkpoints 某行的 channel_versions[channel] = N → 精确指向 blobs 里 WHERE channel=channel AND version=N 那条。下面用真实 JOIN 结果证明。

🔬 证据 1：把 step3 的清单逐条 JOIN 到 blobs，5 条全部命中

光看两张分开的表看不出引用关系，那就直接 JOIN。取 step3 的 channel_versions（{messages:5, __start__:2, __pregel_tasks:4, structuredResponse:5, branch:to:model_request:5}），拿每个 (channel, version) 去 blobs 表精确匹配：

SELECT cv.channel, cv.ver AS 清单里的version,
       b.version AS blobs命中的version, b.type, length(b.blob) AS 字节数
FROM checkpoints c
CROSS JOIN LATERAL jsonb_each_text(c.checkpoint->'channel_versions') AS cv(channel, ver)
LEFT JOIN checkpoint_blobs b
  ON b.thread_id = c.thread_id AND b.channel = cv.channel AND b.version = cv.ver
WHERE c.thread_id = '...7635e622f624' AND c.metadata->>'step' = '3';
清单里的 channel清单里的 versionblobs 命中的 versiontype字节数命中?
__pregel_tasks44json7✓
__start__22empty—✓
branch:to:model_request55empty—✓
messages55json14305✓
structuredResponse55json27✓

5 条全部 ✓ 命中，无一落空。这就是"引用"的直接证据——checkpoint 的清单里写了什么 (channel, version)，blobs 表里就一定有对应那一行实际数据。反过来，把某个 checkpoint 的所有清单项 JOIN 出来拼起来，就还原出这一步的完整状态。

🔬 证据 2：messages 每步指向不同 blob 行，字节数随对话增长

version 递增不是编号游戏——每个新 version 是一份全量的、更长的消息历史。看 blob 字节数随 step 单调变大，正好对应 §7 里消息从 1 条长到 6 条：

step引用的 messages 版本blobs 命中行该 blob 字节数对应内容（见 §7）
02v2990仅 Human 问题
13v32349+ AI 发起 tool_call
24v46489+ ToolMessage（抓回正文）
35v514305+ extract-1 结构化答案等

字节数 990 → 2349 → 6489 → 14305，是"消息越攒越多"的物理证据。每个 step 的 channel_versions.messages 精确指到对应大小的那一行。

🔬 证据 3：同一个 blob 行被多个 checkpoint 共享（去重）

反向查：拿 blobs 里的某一行，看有几个 checkpoint 的清单在引用它。结果证明"没变的 channel 不重复存"：

blob 行（channel:version）引用它的 steps被几个 checkpoint 引用
__start__:1-11
__start__:20, 1, 2, 34 ← 一行被 4 个 checkpoint 共享
__pregel_tasks:311
__pregel_tasks:42, 32 ← 一行被 2 个 checkpoint 共享
结论 · 版本去重共享

__start__:2 这一行 blob 数据，被 step 0/1/2/3 四个 checkpoint 的 channel_versions 同时指向；__pregel_tasks:4 被 step 2、3 共用。某个 channel 这一步没变，就不写新 blob 行，多个 checkpoint 的清单指向同一行。这就是为什么 blobs 仅 13 行却能支撑 5 个 checkpoint 的完整状态——每个 checkpoint 的完整状态 = 按它的 version 清单去 blobs 拼各 channel，共用的部分共享同一行。

样本 thread 全部 blobs（按 channel/version，共 13 行）：

channelversions被哪些 step 引用含义
messagesv2, v3, v4, v50 / 1 / 2 / 3（各不同）对话消息历史，逐版本全量增长
structuredResponsev53结构化输出 channel（本例为 undefined，见 §7.3）
__start__v1, v2v2 被 0/1/2/3 共享入口 channel
branch:to:model_requestv2–v52 / 3 / 4 / 5LangGraph 分支控制
__pregel_tasksv3, v4v4 被 2/3 共享Pregel 引擎调度

§5checkpoints ← checkpoint_writes：下一步的"预写日志"

writes 表的 checkpoint_id 指向产生这批写操作时所在的 checkpoint。LangGraph 执行到某 checkpoint 后，task（调 LLM / 执行工具）先把结果作为 writes 落盘（崩溃可恢复），推进到下一个 checkpoint 时再合并、升成新 blob 版本。

ckpt 59d005e3b23a(step-1)  task 1aff8b37: messages[0], branch:to:model_request[1]
ckpt fdbfff889324(step 0)  task 86345aaf: messages[0], __pregel_tasks[1]
ckpt 96d611d4a949(step 1)  task 9ac07990: messages[0], branch:to:model_request[1]
ckpt 44a94fee8182(step 2)  task a4f85ebd: messages[0]

对照即懂：step-1 的 write 往 messages 写 → 合并后成为 step 0 的 messages:v2；step 0 的 write → 成为 step 1 的 messages:v3……task_id 区分同一步的不同任务，idx 是同一 task 内多个写的顺序号。

§6关联关系全景图

                    thread_id = literary:9ec4f893-...7635e622f624
                                    │ (贯穿三表的总 key)
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
   checkpoints                 checkpoint_blobs            checkpoint_writes
  (快照索引/链表)                (状态数据仓库)               (预写增量)
        │                           ▲                           │
   parent_checkpoint_id             │ 按(channel,version)引用    │ checkpoint_id
   ↺ 自引用成链              channel_versions 指向 blob        指向"产生它的那个 ckpt"
        │                           │                           │
        └──── channel_versions ─────┘                           │
              (JSONB 清单)                                        │
                    ▲                                            │
                    └────────── 合并 writes 升成新 version ◄──────┘

串起来：checkpoints 是目录（每步引用哪些 channel 的哪个 version），checkpoint_blobs 是被引用的实际内容（版本化、跨 checkpoint 去重共享），checkpoint_writes 是每步任务产出、尚未合并进下一快照的增量日志。三者用 thread_id 绑定，用 version 号和 checkpoint_id 互相引用。

§7一次回合的完整轨迹（decode 实证）

问题：给定盖茨比原文 URL，问 ① 含 Gatsby 的行数 ② 首个含 Daisy 的行号 ③ 两句梗概。下面逐步 decode messages channel 的 BYTEA（type=json，UTF-8 直接可读）。

§7.1 step 1 · AIMessage 发起 tool_call（messages v3）

模型没直接答，而是请求调工具。content 为空、tool_calls 有值——标准的"请求调工具"形态：

[0] HumanMessage   原始问题
[1] AIMessage
    ┌─ TOOL_CALL  name: fetch_text_from_url
    │  id:   019f2d9d44472bcf9b06c5c4440fc931
    │  args: {
    │    "url": "https://www.gutenberg.org/files/64317/64317-0.txt",
    │    "substrings": ["Gatsby", "Daisy"]
    │  }
    └─

args 与 UI "参数"面板完全一致，证明 UI 就是从这个 blob 反序列化渲染的。

§7.2 step 2 · ToolMessage 靠 tool_call_id 对上（messages v4）

请求↔结果的唯一关联字段是 tool_call_id，不靠顺序，即使并行多个调用也能一一对上：

 AIMessage.tool_calls[0].id  =  019f2d9d...0fc931
                                          ║  完全相同
 ToolMessage.tool_call_id    =  019f2d9d...0fc931

ToolMessage（lc id: [langchain_core, messages, ToolMessage]，status: success）的 content 是工具返回的 JSON：

{
  "ok": true,
  "totalLines": 6407,
  "totalCharacters": 270822,
  "lineStats": [
    { "substring": "Gatsby", "lineCount": 258, "firstLineNumber": 6, ... },
    { "substring": "Daisy",  "lineCount": 184, "firstLineNumber": 181,
      "firstLineText": "Buchanans. Daisy was my second cousin once removed, and I'd known Tom" }
  ],
  "note": "Line numbers are 1-based. Substring matching is case-sensitive..."
}

§7.3 step 3 · 最终答案藏在 extract-1 的 args 里（messages v5）

关键发现：最终答案不在 structuredResponse channel（该 blob decode 出来是 {"lc":2,"type":"undefined"} 占位符），而是藏在一个名为 extract-1 的工具调用的 args 里。messages v5 共 6 条：

[0] HumanMessage                      原始问题
[1] AIMessage    tool_call: fetch_text_from_url  (id=019f2d9d…0fc931)
[2] ToolMessage  ← fetch 返回统计 JSON
[3] AIMessage    tool_call: extract-1             (id=019f2d9d…53d7)   ★ 答案在这
[4] ToolMessage  ← extract-1 回执
[5] AIMessage    content = "结构化响应已生成。"     收尾

回想 agent-runner.ts 的 isStructuredResponseTool 判断 toolName.startsWith("extract-")——就是它。definition 配了 responseFormat，LangChain 把"生成结构化答案"实现成调 extract-1 工具，模型把结构化字段当 args 传入：

{
  "answer": "## 结果\n\n### 1) 包含 Gatsby 的行数\n**258 行**...\n
             ### 2) ...第 181 行...\n### 3) 两句话中性梗概\n
             F. Scott Fitzgerald 的《了不起的盖茨比》...",
  "confidence": 0.99,
  "keyFacts": [
    "工具返回 Gatsby 的 lineCount=258（大小写敏感，按行计数）",
    "工具返回 Daisy 的 firstLineNumber=181，对应行内容为 'Buchanans...'",
    "文件总行数 6407，总字符数 270822",
    "匹配规则：大小写敏感，每行最多计一次，行号为 1-based"
  ],
  "toolResults": [{ "summary": "成功获取 Gutenberg 纯文本...", "toolName": "..." }]
}

args.answer 里的 Markdown 就是 UI 上一字不差的最终答案，也是 getStructuredAnswer(result) 读的 .answer 字段。

数据溯源闭环——每个数字都能追

fetch 返回 (step2 ToolMessage)extract-1 答案 (step3)UI 显示
lineStats[Gatsby].lineCount = 258answer: "258 行"258 行

模型没编数字——keyFacts 与 how_you_computed_counts 明确写了数据来源，忠实执行了 prompt "不能编、要说明怎么算"的要求。

⚠ 值得留意的实现盲区

structuredResponse:v5 这个 channel 持久化的是 undefined——结构化结果没落到该 state channel，而是以 extract-* tool_call args 形式存在于 messages 里。运行时 getStructuredResponse(result) 从内存返回值取，但 checkpoint 里这个 channel 是空的。若想从数据库直接重建历史答案（而非靠内存返回值），需 parse messages 里 extract-* 的 tool_call args，不能指望 structuredResponse channel。

§8常用查询 SQL

列出全部 thread 及 checkpoint 数

SELECT thread_id, COUNT(*) AS checkpoint_rows
FROM checkpoints GROUP BY thread_id ORDER BY thread_id;

看某 thread 的 checkpoint 链与版本清单

SELECT RIGHT(checkpoint_id,12) AS ckpt,
       RIGHT(COALESCE(parent_checkpoint_id,'—'),12) AS parent,
       metadata->>'step' AS step,
       checkpoint->'channel_versions' AS channel_versions
FROM checkpoints
WHERE thread_id = 'literary:9ec4f893-...7635e622f624'
ORDER BY checkpoint_id;

按 channel_versions 还原某 checkpoint 的完整状态（JOIN blobs）

SELECT b.channel, b.type, b.blob
FROM checkpoints c
CROSS JOIN LATERAL jsonb_each_text(c.checkpoint->'channel_versions') AS cv(channel, ver)
JOIN checkpoint_blobs b
  ON b.thread_id = c.thread_id
 AND b.channel   = cv.channel
 AND b.version   = cv.ver
WHERE c.checkpoint_id = '...503b5efc4ea5';

decode 某个 messages blob（type=json 时）

SELECT convert_from(blob,'UTF8')
FROM checkpoint_blobs
WHERE thread_id = 'literary:9ec4f893-...7635e622f624'
  AND channel = 'messages' AND version = '4';
-- 管道给 python3/jq 美化即可看到 tool_calls / tool_call_id

§9结论

从"用户提问 → 抓原文 → 统计 → 结构化成答案 → 渲染"整条 agent 回合，全部可从这三张 checkpoint 表 + messages channel 的版本演进里完整还原。这就是 LangGraph checkpointer 持久化的价值：

不只存最终结果，而是存下整个推理轨迹，可回溯、可续跑、可审计每个数字的来源。

  • checkpoints = 快照索引 + 时间链（parent 自引用）
  • checkpoint_blobs = 版本化状态仓库，跨 checkpoint 去重共享
  • checkpoint_writes = 每步的预写增量，合并后升版
  • 请求↔结果靠 tool_call_id 缝合，历史靠 messages 版本递增累积
  • 三表用 thread_id 绑定，agentId:threadId 前缀隔离多 agent
