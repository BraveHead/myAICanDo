M10 · execute_command 端到端时序

从用户点“批准”到命令终态回写对话流的完整链路。核心是把 HTTP 请求生命周期与任务生命周期彻底拆开：审批接口毫秒级返回 202，命令在独立 Bun Worker 进程 + PostgreSQL 中运行，浏览器刷新 / 切线程 / 断连都不影响任务。

PostgreSQL 全局 BIGSERIAL 事件 ID heartbeat 5s / lease 15s SSE Last-Event-ID 续传 stdout/stderr 8 KiB 背压分片 worker_lost 永不自动重跑
请求 / 调用 返回 / 事件下发 回写对话流（LLM 续接） 周期性动作 / 备注

关键机制拆解

两条生命周期解耦

  • 审批接口在事务提交后立即返回 202，HTTP 请求结束。
  • 命令在 bun src/workers/command-execution-worker.ts 独立进程执行。
  • 刷新 / 切线程 / 浏览器断开只释放 SSE 订阅，不触碰任务。

实时输出 + 真实背压

  • 子进程输出先 pause()，等事件写库完成再 resume()。
  • UTF-8 安全分片 ≤ 8 KiB，逐条落 command_output 事件。
  • 没有任何浏览器连着，输出也已持久化，不会丢。

Last-Event-ID 续传 · 去重

  • 事件表 id BIGSERIAL 全局单调递增。
  • 服务端只发 id > cursor；客户端 reduce 再挡 id ≤ lastEventId。
  • 快照 + SSE 重叠部分被双层去重吃掉，刷新不重复不缺片段。

终态回写对话流

  • 任一终态都在同事务更新 pending_action 的 result。
  • 对话从持久化的 pending action 恢复，而非依赖 HTTP 请求。
  • worker_lost 永不自动重跑；重试是新授权、新 execution。
