Human-in-the-loop v1：Memory 写入/删除确认流

v1 只拦截 save_memory 和 delete_memory。Agent 触发高风险记忆操作时，先创建服务端 pending action 并暂停 SSE；用户确认后，服务端按已保存的 args 执行真实 memory service。

5. 展示确认卡片

SSE 收到 tool_call.requires_action 后，assistant-ui 将消息标记为 requires-action 并展示确认/取消按钮。

Chat Runtime

2. 发起 chat SSE

chat-runtime-provider 调用 /api/tenants/:tenantId/chat，并携带当前 threadId。

7. 调用 approval API

恢复 run 时检测到已决 approval，转而请求 /chat/approvals，不再重新调用普通 chat。

10. 回填最终文本

将 approval API 返回的 final text 和 structured response 追加到当前 assistant message。

Agent Runner

3. 模型调用 memory 工具

Memory Agent 或 Coordinator 调用 save_memory / delete_memory。

4. 拦截并暂停

middleware 识别 gated tool，创建 pending action，发出 requires-action tool card，然后结束当前 SSE。

8. 不信任前端 args

approval API 只读取服务端保存的 pending action 和 args，前端只提交 approvalId、approved、reason。

Postgres

Pending Action 表

assistant_pending_actions 保存 action、tool、args、 status、result，并按 tenant/user/thread 隔离。

9. 执行 memory service

确认后写入或删除 assistant_memories；取消则标记 rejected，不改长期记忆。

11. 持久化对话结果

最终文本写回 thread repository，侧边栏更新时间可正常刷新。

关键边界

v1 scope

安全边界

  • 只 gate 两个工具： save_memory 和 delete_memory。
  • 只信任服务端 args： approval API 不接受前端回传工具参数，避免篡改写入内容。
  • 租户隔离： pending action 和 memory 都按 tenant/user/thread 范围查询。
  • 默认 30 分钟过期： 过期 action 不允许执行，需要重新发起。

后续 v1.1 建议

  • 刷新页面后恢复 pending approval 卡片。
  • 把 confirmed tool result 直接回填到原工具卡片。
  • 增加 pending action 管理 API，便于排查和撤销。
  • 将高风险 filesystem 写操作和外部 API 调用纳入同一 approval 框架。
