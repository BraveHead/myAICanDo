M11 标准 MCP 接入与只读 Server 数据流

M11 在现有领域服务之外增加一个标准协议适配层，让 Codex、Claude Desktop、Cursor 或其他 MCP Host 在不理解项目内部 LangChain Tool 实现的情况下，安全读取当前用户有权访问的命令执行记录和线程文件。 首版使用独立 Bun stdio 进程，只面向受信任的本机客户端，不改变现有 Agent、Skill、审批与 Worker 链路。

MCP TypeScript SDK v2 Bun stdio Server 4 个只读工具 tenant / user 固定身份 workspace / thread 每次校验 无数据库迁移

为什么 M11 是必要的

问题 1：内部 Tool 不是跨进程协议

当前 LangChain Tool 只能由项目内 Agent 直接装配。外部 AI 客户端若要读取相同数据， 必须了解项目模块、运行上下文和调用参数，无法通过统一发现机制接入。

解决 1：通过 MCP 暴露稳定能力契约

MCP Client 可通过 tools/list 自动发现名称、说明、Schema 和只读属性， 再使用同一 JSON-RPC 约定调用，不需要依赖 LangChain 或项目页面 API。

问题 2：重复实现容易绕过安全边界

如果每个客户端各自查询 PostgreSQL 或遍历沙盒目录，容易遗漏 tenant、user、workspace、thread 隔离，以及相对路径、symlink、二进制和文件大小限制。

解决 2：协议适配复用既有领域服务

MCP Handler 只负责参数校验、scope 鉴权与结果转换；执行查询和文件读取仍复用 command-execution 与 filesystem-service，安全规则只有一个事实来源。

问题 3：Skill、Agent Tool 与外部能力边界混淆

Skill 可以携带说明和脚本，但它描述的是“如何完成任务”；内部 Tool 解决进程内调用， 二者都不天然提供跨客户端的发现、Schema 协商和传输协议。

解决 3：明确三层职责而不互相替换

Skill 继续定义工作流，内部 Agent 继续直连 Tool，MCP 只作为外部客户端适配层。 首版不增加 Agent → MCP → 本项目的自调用和额外故障点。

架构分层

MCP Host / Client

负责按配置启动子进程、完成 initialize、发现工具并发起调用； 例如 Codex、Claude Desktop、Cursor 或 MCP Inspector。

↓ stdio / JSON-RPC
进程入口

src/mcp/stdio-server.ts 读取固定身份与数据库配置，创建 Server， 绑定信号和 stdin 关闭事件；stdout 只输出协议，诊断日志只进入 stderr。

↓
默认 Server 组装层

default-server.ts 使用编译期静态注册表组合 Access Policy、 command-execution 和 filesystem 工具包；新增领域工具不需要修改 Server factory。

↓ 静态工具定义
MCP Core

server-factory.ts 只创建 Server、校验工具名称并注册定义；统一执行管线负责 requestId、thread scope 授权、成功/错误结果与调用日志，不依赖具体领域服务。

↓ trusted scope
领域工具模块

tools/command-execution 与 tools/filesystem 分别拥有自己的 Schema、最小领域 Port、结果投影和错误转换，不再共享聚合 Service 容器。

↓ 每次调用重新授权
Access Policy / Repository

Policy 验证固定 tenant/user 身份、租户成员关系、workspace 归属和 thread 绑定； Repository 独占 PostgreSQL 行映射，不依赖 Next Cookie 或 server-only。

↓ trusted scope
既有领域服务

命令工具调用 execution-service，文件工具调用 filesystem-service；MCP 不复制查询上限、输出裁剪和文件沙盒规则。

↓
数据与文件层

PostgreSQL 保存 SaaS scope、thread 和 M10 execution；本地 sandbox 仍按 tenant/user/thread 隔离。M11 不新增表，也不触碰命令执行状态机。

关键边界： 浏览器中的 myAICanDo Agent 仍通过 AgentHarness 直接调用内部 Tool；MCP Server 是由外部 Host 启动的独立进程。 两条链路共享领域服务与安全规则，但不互相代理，也没有启动先后依赖；MCP 工具注册表是显式 allowlist， 不扫描目录或动态加载第三方模块。

七阶段数据流

阶段 1
Host 启动可信本机边界
1

MCP Host 直接使用 Bun 可执行文件和 src/mcp/stdio-server.ts 的绝对路径启动子进程。

2

入口读取 DATABASE_URL、MCP_TENANT_HASH_ID、MCP_USER_HASH_ID，缺少必填配置时向 stderr 报错并退出。

阶段 2
协议协商discover / initialize / tools/list
3

Client 与 Server 通过新版 server/discover 或兼容旧版的 initialize 完成协议协商，Server 声明名称 my-ai-can-do-mcp 和项目版本。

4

Client 调用 tools/list，获得四个工具的中文说明、严格输入/输出 Schema 和只读 annotations。

阶段 3
请求校验拒绝额外字段
5

SDK 按 Zod Schema 校验 workspaceId、threadId、工具特有参数和 limit；未知字段直接拒绝。

6

tenant/user 永远取自进程环境，不接受模型参数覆盖；每次调用生成独立 requestId 贯穿日志与错误结果。

阶段 4
Scope 鉴权每次调用都验证
7

Access Policy 查询用户、租户成员关系和租户状态，再验证 workspace 属于该租户且可访问。

8

确认 thread 已持久化并绑定固定 tenant/user/workspace；不匹配时返回稳定错误，不进入领域服务。

阶段 5
领域调用复用项目规则
9

execution 工具使用可信 scope 查询 M10 任务；列表只返回轻量字段，详情才返回受上限约束的 stdout/stderr/result。

10

filesystem 工具复用线程沙盒路径解析与 UTF-8、symlink、二进制、256,000 bytes 和最多 200 项限制。

阶段 6
结果投影content + structuredContent
11

成功响应同时返回机器可消费的 structuredContent 和 JSON 文本 content，并符合声明的输出 Schema。

12

可预期业务失败返回 isError: true 与稳定错误结构；未知异常只对 Client 暴露 internal_error，细节写 stderr。

阶段 7
关闭与诊断不污染协议通道
13

SIGINT、SIGTERM 或 stdin 关闭时停止接收调用，关闭 transport 和 PostgreSQL 连接池后退出。

14

结构化日志记录 requestId、工具名、状态和耗时但不记录 DATABASE_URL、完整文件内容或完整命令输出。

四个只读工具协议

工具 输入 成功输出 边界
list_command_executions workspaceId、threadId、可选 limit，默认 20、最大 100 轻量 execution 列表、数量；包含 ID、命令、状态、attempt、重试链、摘要、截断标记和关键时间。 不返回 stdout、stderr 和 result；不订阅 SSE。
get_command_execution workspaceId、threadId、executionId 完整 CommandExecutionSnapshot，包含受 M10 上限约束的输出和最终结果。 只查询当前 scope；不存在时返回 execution_not_found。
list_workspace_files workspaceId、threadId、可选 path，默认 . ListFilesystemDirectoryResult，包含逻辑路径和最多 200 个目录项。 拒绝绝对路径、..、symlink 和越出当前线程沙盒的路径。
read_workspace_file workspaceId、threadId、path ReadFilesystemFileResult，包含路径、UTF-8 文本、大小和摘要。 拒绝目录、二进制、symlink 和超过 256,000 bytes 的文件。

四个工具统一声明 readOnlyHint: true、destructiveHint: false、 idempotentHint: true、openWorldHint: false。 首版不注册入队、取消、重试、文件写入、Skill 脚本执行或 checkpoint 恢复工具。

统一响应和错误

成功结果

{
  "ok": true,
  "...": "与具体工具 outputSchema 对应的字段"
}

同一对象作为 structuredContent，并序列化为文本内容，兼容只读取文本的 Host。

业务错误

{
  "ok": false,
  "error": {
    "code": "thread_workspace_mismatch",
    "message": "线程未绑定到指定工作区。",
    "requestId": "..."
  }
}

错误响应设置 isError: true；未知异常统一转换为 internal_error，不泄漏堆栈和数据库信息。

本地 stdio 客户端配置

推荐配置形态

MCP Host 必须直接启动 Bun，使用 Bun 和入口文件的绝对路径。下面仅为结构示例， DATABASE_URL 应通过本机密钥或进程环境注入，不要把真实凭据提交到仓库。 

{
  "mcpServers": {
    "my-ai-can-do": {
      "command": "/absolute/path/to/bun",
      "args": [
        "/absolute/path/to/myAICanDo/src/mcp/stdio-server.ts"
      ],
      "env": {
        "DATABASE_URL": "postgresql://<user>:<password>@127.0.0.1:5432/<database>",
        "MCP_TENANT_HASH_ID": "tenant_demo",
        "MCP_USER_HASH_ID": "user_demo",
        "FILESYSTEM_SANDBOX_ROOT": "/absolute/path/to/var/agent-files"
      }
    }
  }
}

不要把 yarn mcp:stdio 配成 Host command： Yarn 的启动横幅可能写入 stdout 并破坏 JSON-RPC。项目脚本仅用于开发者诊断， 实际 Host 配置应直接执行 Bun。

启动关系

POSTGRESQL

必需依赖

MCP Server 启动和 scope/execution 查询需要数据库可连接；数据库不可用时应快速失败。

MCP HOST

按需拉起

客户端使用时自动启动 stdio 子进程；退出客户端或关闭连接时结束该进程。

YARN DEV

无启动依赖

MCP 直接调用运行时无关的领域服务，不经过 Next.js Route Handler，因此不要求 Web 服务运行。

COMMAND WORKER

读取时非必需

四个工具不创建或改变任务；Worker 停止时仍可读取已有 execution，只是不会有新后台命令推进。

因此本地读取场景只有一个硬性顺序：先保证 PostgreSQL 可连接，再由 MCP Host 启动 Server。 yarn dev 和 yarn worker:commands 是否运行取决于页面与命令执行需求，不是 MCP 只读 Server 的前置条件。

安全边界

首版具备

  • 受信任本机 stdio，不监听网络端口。
  • 进程级 tenant/user 身份，不由模型传入。
  • workspace/thread 每次调用重新鉴权。
  • 严格 Schema、只读 annotations、四工具 allowlist。
  • 复用既有 execution 与 filesystem 限制。
  • stdout 协议专用，stderr 脱敏诊断。

首版不提供

  • 不提供远程用户认证或公网访问。
  • 不把本机环境变量视为可移植的 HTTP 身份凭证。
  • 不执行命令、不修改文件、不取消或重试任务。
  • 不执行 Skill 携带的脚本。
  • 不自动恢复 Agent，不注入完整输出到 Agent 上下文。
  • 不允许客户端绕过 scope 直接指定文件系统根路径。

未来演进到 Streamable HTTP

远程 MCP 不是把 stdio transport 换成 HTTP 即可。未来应保留 Server factory、工具 Schema、 access policy 和领域适配器，另建独立的 Streamable HTTP 入口，并补齐下面的远程安全面：

  1. 身份：使用 Bearer Token 或 OAuth，把 tenant/user 从服务端验证后的凭证生成，禁止复用 MCP_TENANT_HASH_ID / MCP_USER_HASH_ID。
  2. 会话：定义 MCP session 生命周期、断线恢复和服务端水平扩展策略，不依赖单机进程状态。
  3. 边界：增加 Origin/Host 校验、TLS、请求体上限、超时、限流和并发控制。
  4. 审计：持久化调用主体、工具名、scope、状态、耗时和 requestId，并对敏感字段脱敏。
  5. 部署：将远程 MCP 视为独立长期运行服务，不由 Next.js 请求临时承担，也不与命令 Worker 混为同一进程。

这一路径保证协议层可以复用，同时明确隔离“可信本机进程配置”和“远程多用户认证”两套完全不同的信任模型。
