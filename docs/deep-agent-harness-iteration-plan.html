myAICanDo Deep Agent Harness 迭代计划

目标不是把项目整体迁移到 Python 版 Deep Agents，而是在当前 Next.js + LangChain + LangGraph checkpoint 的 TypeScript 架构上，逐步补齐 Deep Agents 中最基础的 agent harness 能力：文件系统、计划、上下文管理、子代理、长期记忆、人工确认和可观测流。
生成日期：2026-07-14 最近更新：2026-07-15 项目：myAICanDo 技术基线：LangChain createAgent + LangGraph checkpointer 推荐首个功能：filesystem v1.1

§1目标

一句话目标： 在现有 agent runner 上抽出一个本地 AgentHarness 层，让普通 LangChain agent 获得 Deep Agents 风格的基础脚手架能力，而不破坏当前 tenant/user/thread 隔离、assistant-ui 线程存储、LangGraph checkpoint 和已有 memory approval 流程。

保持现有架构

继续使用 langchain 的 createAgent、当前模型配置、现有 /api/tenants/[tenantId]/chat 路由和 thread-store。

补齐 harness 能力

按功能增量添加 filesystem、write_todos、task、context offloading、skills、memory、human-in-the-loop。

避免一次性重写

每一步都能独立上线、独立验证。先做可见能力，再做抽象收敛和体验增强。

§3目标 Harness 架构

建议新增本地 harness 层，而不是把能力继续散落在各个 agent definition 里。这个层只负责“Deep Agent 风格脚手架”，具体业务 agent 仍由 AgentDefinition 描述。

UI / API 层
chat-workspace.tsx、/api/tenants/[tenantId]/chat、SSE 事件、approval 操作。
↓
AgentHarness 层
组装内置工具、计划状态、filesystem、skills、memory、subagents、权限、context 策略和事件投影。
↓
LangChain Agent 层
createAgent、model、tools、system prompt、middleware、responseFormat。
↓
LangGraph Runtime
checkpoint、thread_id、恢复、持久化执行、部分 human-in-the-loop 基础能力。
↓
项目存储
Postgres thread-store、memory-store、pending-action-store、filesystem sandbox。

§4迭代路线

M0

抽出 AgentHarness 外壳

这是技术铺垫，不做复杂功能。目的是让后续内置工具、prompt 拼装、事件投影、权限策略有统一入口。

改动 新增 AgentHarnessConfig、createHarnessedAgent()，内部仍调用当前 createAgent()。
范围 只迁移 checkpointer、middleware、systemPrompt 拼装入口，不改业务行为。
验收 现有 demo/weather/literary/filesystem/memory/coordinator 全部保持可运行；typecheck 和 lint 通过。
M1

Filesystem v1.1：从只读沙盒升级为基础文件工作区

这是推荐第一个功能。当前已有只读 sandbox，路径安全和租户隔离都在，最容易变成真正 Deep Agents 风格的 virtual filesystem。

改动 增加 write_file、edit_file、delete_file、glob_files；保留当前 list/read/search。
安全 引入 declarative permissions：默认只允许 workspace/** 和 notes/** 写入，禁止 .env、绝对路径和 ..。
验收 文件可创建、读取、精确替换、删除；危险路径返回明确错误；写/删操作先走 approval。
M2

Planning v1：实现 write_todos 和任务状态（已落地）

Deep Agents 的计划层本质是让 agent 对多步任务有稳定状态，而不是只靠 prompt 说“先计划”。

改动 已新增 write_todos 工具，todo 支持 pending/in_progress/completed，按 tenant/user/thread 保存到项目表或内存 fallback。
UI 已扩展 ChatStreamEvent，输出 todo_update，前端可展示紧凑任务列表。
验收 对“分析文件并产出报告”这类任务，agent 会先写 todos，执行中更新状态，最终全部完成或解释阻塞。
M3

Context v1：系统 prompt 分层与工具结果 offloading

当前 memoryContext 是直接拼到 system prompt；长工具结果也容易污染主上下文。这里开始建立真正的 context management。

改动 把 prompt 拆成 base、agent、memory、skills、tool-guidance 五段。
Offloading 大文件读取、大搜索结果写入 .context/offloads/*.json artifact，主上下文只保留摘要和文件引用。
验收 同一任务读取大文件时不会把全部内容塞回最终主消息；日志能看到 offload 文件路径和摘要。
M3 最终设计： prompt 固定拆成 base、agent、memory、skills、tool-guidance 五段； 默认当 JSON 工具结果超过 12000 bytes，或 read_filesystem_file.content 超过 8000 字符时 offload。 artifact 保存原始结果、摘要、工具名、参数和大小；返回给模型与 SSE 的工具结果只保留 summary、offloaded、artifactPath、originalSizeBytes。 工具完成后的 checkpoint 恢复重试会额外发送 agent_retry SSE，向页面说明重试原因，但不把已成功的工具卡标记为失败。 .context 是 harness 内部目录，普通文件写入工具仍只能修改 workspace/** 和 notes/**，approval 流程不变。
M4

Subagents v1：把 coordinator 委派升级为真正 task 工具

当前 coordinator 只是调用委派工具，并没有启动隔离的子 agent。Deep Agents 的 subagent 重点是上下文隔离和单次结果回传。

改动 新增 task 工具，可选择 filesystem、memory、weather 等子 agent。
隔离 子 agent 使用独立 thread_id：parentThread:subtaskId:agentId，只返回 final report。
验收 coordinator 能把“查记忆 + 搜文件 + 总结”拆给不同子 agent，主上下文只收到每个子任务的最终摘要。
M5

Skills v1：按需加载领域能力

Skills 用于把稳定工作流、项目约定和工具使用规则做成可复用能力，避免每个 agent prompt 越写越长。

改动 约定 agent-skills/*/SKILL.md，启动时只读取 frontmatter 和 description。
工具 新增 list_skills 和 read_skill，需要时再读取全文、模板或脚本路径。
验收 新增一个 filesystem 报告 skill 后，agent 能在相关任务中主动读取并按该流程执行。
M5 最终设计： 项目级 skill 放在 agent-skills/<skillId>/SKILL.md； harness 启动时只把 id/name/description/triggers 摘要注入 ## skills； 模型需要完整流程时调用只读 read_skill。 M5 不执行脚本、不新增 SSE 事件、不改变子 agent 的工具权限。
M6

Memory v2：统一用户记忆、项目记忆和 harness memory

当前长期记忆是业务自建，能用但和 filesystem/context/skills 还没有统一。这里把它接入 harness 层。

改动 将 memory-store 继续作为事实存储，增加 memory_manifest 注入和 AGENTS.md 风格项目记忆读取。
边界 用户偏好仍按 tenant/user 隔离；项目规则只按 tenant/workspace 隔离，不引入 assistantId；两者在 prompt 中分段。
验收 agent 能区分用户偏好、workspace 项目规则、当前线程临时上下文；保存/删除仍需 approval；workspace 切换不会串线程或 checkpoint。
M6 v1 已落地： 新增 opaque workspaceId 和 assistant_workspaces，thread/todo/checkpoint 都纳入 workspace 维度；旧 URL 会解析后跳转到 /:tenantId/workspace/:workspaceId/chat/:threadId。 项目记忆只读取 <FILESYSTEM_SANDBOX_ROOT>/<tenantHashId>/workspaces/<workspaceId>/AGENTS.md，拒绝 symlink、越权路径和超限文本；普通 filesystem 工具不能访问该文件。 Harness 使用统一 MemoryManifest，并对 agent、coordinator、subagent 和 fallback model 使用同一份 user/project/harness 三段上下文。
M7

Human-in-the-loop v2：统一敏感工具审批

Deep Agents 中 HITL 覆盖敏感工具调用。当前项目只覆盖 memory mutation，应扩展到文件写入、删除、外部 API 和子任务执行。

改动 把 APPROVAL_GATED_TOOL_NAMES 从静态数组升级为 tool policy registry。
决策 支持 approve、reject、edit args、respond with guidance 的最小版本。
验收 write_file/delete_file/save_memory/delete_memory 都会产生可审查预览；拒绝后 agent 能继续解释替代方案。
M7 实施边界： 本轮只覆盖 write_file、edit_file、delete_file、save_memory、delete_memory。 审批策略统一进入 registry，pending action 增加 workspace_id 和 executing 原子领取状态；支持确认、拒绝、修改参数并执行、提供指导四种决策。 guidance 不直接恢复原 checkpoint，而是拒绝当前副作用后，由前端在相同 workspace/thread 发起新的普通聊天回合。 task 和外部 API 只保留扩展点，M7 不启用其审批执行。
M8

Streaming v2：投影 todos、subagents、filesystem 操作

当 harness 能力变多后，只看最终答案不够。需要把用户关心的状态以结构化事件投影到前端。

改动 扩展 ChatStreamEvent：todo_update、subagent_start/end、filesystem_change。
UI 在聊天区展示任务列表、子任务轨迹、文件变更摘要，不展示大段内部日志。
验收 长任务中用户能看到当前正在执行哪一步、哪个子 agent 在工作、改了哪些文件。
M9

Sandbox / Execute：最后再做代码执行能力

shell/code execution 风险最高，应该在 filesystem permissions、approval、event streaming 都稳定后再接。

改动 先设计 execute_command 协议，不直接开放本机 shell；优先接隔离容器或受限 runtime。
安全 命令 allowlist、超时、输出截断、网络策略、密钥隔离、approval 必须先完成。
验收 能跑安全的只读命令和测试命令；危险命令被拦截；所有执行记录可审计。

§5第一步建议

下一步建议从 M7：Human-in-the-loop v2 开始。 M0-M6 的 Harness、filesystem、planning、context offloading、subagents、skills 和 workspace memory 已形成基础；当前应先统一敏感工具审批、执行幂等和 workspace scope，再继续扩展 Streaming v2。

M7 的拆分顺序

  1. 先建立审批 policy registry，统一五类文件/用户记忆 mutation 的参数校验、预览和执行器。
  2. 扩展 pending action 的 workspace scope，增加历史 workspace 回填、executing 原子领取和重复提交保护。
  3. 扩展 approvals API，兼容旧 approved 请求，并支持 approve、reject、edit_args、guidance 四种决策。
  4. 调整 Agent runner、SSE 和审批卡片，增加参数编辑与 guidance 输入；guidance 通过普通 chat 回合继续执行。
  5. 补齐 tenant/workspace/thread 隔离、幂等执行、过期处理和 Chrome 回归验收，再进入 M8 Streaming v2。

§6总体验收标准

能力验收

  • agent 能维护 todo，并在长任务中更新任务状态。
  • agent 能在隔离 sandbox 中读写工作文件，且权限明确。
  • coordinator 能启动隔离子 agent，并只接收最终摘要。
  • 大文件和大结果不会直接塞满主上下文。
  • 敏感操作必须暂停等待用户确认。

工程验收

  • fnm exec --using .node-version bun run typecheck 通过。
  • fnm exec --using .node-version bun run lint 通过。
  • 新增 service/tool 的路径逃逸、权限、空输入、超限输入都有测试。
  • Postgres checkpointer 和 thread-store 的隔离 key 都包含 workspace 维度，并兼容旧 key。
  • 现有 demo/weather/literary/memory/filesystem/coordinator 行为不回退。
