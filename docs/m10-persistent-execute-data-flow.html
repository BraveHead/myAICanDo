M10 Persistent Execute 数据流

M10 把 M9 的“审批请求内同步执行”拆成持久入队、独立 Worker 和可恢复订阅三段。 HTTP 请求结束、页面刷新或切换线程都不会影响已经领取的命令；只有用户明确取消或 Worker 关闭才会终止进程。

PostgreSQL only Bun Worker × 2 heartbeat 5s / lease 15s SSE heartbeat 15s 手动重试最多 3 次

为什么 M10 是必要的

M9 痛点 1：请求生命周期等于任务生命周期

M9 在审批 Route Handler 内等待命令结束。请求超时、服务重启或连接中断都会让任务结果失去可靠归属， 长任务也持续占用 Web 请求资源。

M10 结果 1：HTTP 只负责入队

审批与 execution 原子写入 PostgreSQL 后立即返回 202；独立 Bun Worker 继续执行， Web 请求完成不再影响命令生命周期。

M9 痛点 2：只拿到最终输出

用户无法区分排队、运行和卡住，也看不到实时 stdout/stderr；刷新页面后只能依赖聊天历史里的最终卡片。

M10 结果 2：持久事件可恢复

state、output、result 都有全局递增事件 ID。页面按 Last-Event-ID 续传，刷新或切线程后不会丢片段、不会重复输出。

M9 痛点 3：无法可靠取消和重试

浏览器断开与用户取消没有清晰区别，失败后如果复用原任务可能重复执行已经产生副作用的命令。

M10 结果 3：显式控制、永不自动重跑

取消由数据库状态驱动并终止整个进程组；重试是新的 execution 和新的明确授权，最多 3 次，Worker 丢失也不会自动重跑。

主数据流

01 · APPROVAL

用户确认

  • 重新校验 args、cwd、symlink 和 scope
  • 要求 15 秒内存在健康 Worker
  • 重复确认复用已有 execution
02 · TRANSACTION

PostgreSQL 原子入队

  • pending action → executing
  • 插入 queued execution
  • 插入首个 command_state
03 · WORKER

租约领取

  • FOR UPDATE SKIP LOCKED
  • 固定 executionId
  • 定期续租并轮询取消
04 · SANDBOX

受限执行

  • 网络关闭、目录只读
  • stdout/stderr 异步背压
  • 8 KiB UTF-8 安全分片
05 · UI

恢复与续订

  • 按 thread 加载快照
  • Last-Event-ID 补发事件
  • 按 toolCallId 挂回工具卡

按阶段展开的执行步骤

阶段 A
确认与入队
1

Route Handler 校验登录态、tenant/user/workspace/thread scope，并读取 pending action。

2

使用 M9 同一策略重新校验 command、args、cwd、timeout 和 symlink；查询 Worker 15 秒健康窗口。

3

同一数据库事务内把 approval 标为 executing、插入 queued execution 和首个 command_state，返回 HTTP 202。

阶段 B
调度与租约
4

两个 Worker lane 通过 FOR UPDATE SKIP LOCKED 竞争最早 queued 任务，避免重复领取。

5

领取后写入 workerId、running、startedAt 和 15 秒 lease，并持久化 command_state。

6

运行期间每 5 秒续租；lease 失效由维护任务标记 failed(worker_lost)，禁止自动执行第二次。

阶段 C
Sandbox 执行
7

Worker 把数据库 executionId 注入 SandboxExecutor；macOS/Docker 仍沿用 M9 的禁网、只读和 allowlist。

8

子进程输出流先 pause，再等待事件写库完成后 resume，形成真实背压；UTF-8 分片不超过 8 KiB。

9

超时、取消或 SIGTERM 终止整个进程组；Docker 同时按 execution 对应容器名执行清理。

阶段 D
事件与界面
10

前端按当前 thread 拉取最新 100 个快照，再为非终态 execution 建立独立 SSE 订阅。

11

服务端只返回游标后的事件；客户端用事件 ID 再次去重，并把 output 追加到对应 stdout/stderr。

12

provider 按 toolCallId 选择最新 attempt，原 execute_command 工具卡实时显示状态、输出、取消和重试。

阶段 E
终态与维护
13

Worker 原子写入最终 result、command_result 事件，并同步 pending action 的 executed/failed 结果。

14

SSE 在终态事件发送完成后关闭；浏览器断开只释放订阅，不调用取消接口。

15

Worker 定期清理 7 天前事件、30 天前终态 execution 和陈旧 heartbeat。

状态机

queued→running→ completed failed timed_out sandbox_unavailable · queued / running→cancel_requested →cancelled · queued→expired

运行任务 lease 失效时进入 failed(worker_lost)，不自动重新执行。 取消与自然完成发生竞态时，以数据库最终抢占到的终态为准；重试永远创建新的 execution，并通过 rootExecutionId / parentExecutionId 保留链路。

持久化职责

assistant_command_executions

  • tenant / user / workspace / thread 全 scope
  • approvalId、toolCallId、命令参数与 timeout
  • status、attempt、parent/root execution
  • worker、lease、cancel、result 和审计时间
  • 终态元数据保留 30 天

assistant_command_execution_events

  • 全局 BIGSERIAL 事件 ID
  • command_state / command_output / command_result
  • 单个 output payload 不超过 8 KiB
  • 断线按 ID 续传并在客户端去重
  • 事件保留 7 天

接口契约

接口职责关键行为
POST /chat/approvals 命令审批与首次 execution 原子创建 成功返回 202；Worker 不健康返回 execution_worker_unavailable，审批仍可重试。
GET /chat/executions 加载当前线程快照 刷新后恢复运行态和终态输出，不读取其他 scope。
GET /chat/executions/:id/events 可重连 SSE 支持 after / Last-Event-ID；15 秒 heartbeat；终态事件补齐后关闭。
POST /chat/executions/:id/cancel 幂等取消 queued 直接取消；running 标记 cancel_requested，由 Worker 终止进程组与容器。
POST /chat/executions/:id/retry 用户明确重新授权 重新校验参数、路径和 scope，创建新 execution；最多 3 次。

保持不变的安全边界

M10 不扩大 M9 的命令能力：只允许既有 allowlist，限制当前 thread 的 workspace/** 和 notes/**，文件系统只读且网络关闭； 默认超时 30 秒、最大 120 秒，stdout 和 stderr 各 64 KiB、总计 128 KiB。 Sandbox 不可用时返回终态错误，不降级为本机裸 Shell。

后台完成只更新原工具卡，不恢复 Agent checkpoint，也不把完整输出注入 Agent 上下文。 浏览器断开只取消 SSE 订阅；显式“取消执行”才会影响后台任务。
